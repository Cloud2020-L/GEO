# BDD: 模型对比驱动的引用来源增强闭环

## Feature: 基于模型对比 Run 的引用来源增强分析

作为 GEO 内容运营人员，
我希望“引用来源采集”不是一个孤立的新监测入口，
而是基于某一次模型对比 Run 的增强分析动作，
以便系统能复用同一批模拟问题、模型、品牌、域名和竞品，形成从模型对比到来源偏好、文章生成和复测评估的闭环。

## Background

假如系统已经存在模型可见度监测能力
并且系统已经存在 AI 回答来源抽取、来源文章画像和 AI 引用偏好分析能力
并且用户已登录并拥有当前租户或品牌的数据权限
并且至少配置了一个可调用模型

---

## Scenario: 普通模型对比 Run 是主流程

当用户创建一次普通模型对比任务
并选择品牌、域名、模拟问题、模型和竞品
那么系统应按普通用户搜索视角向各模型提问
并且系统应保存每个模型针对每个问题返回的回答
并且系统应统计品牌可见性指标

验收标准：
- 普通模型对比 Run 的 `run_type` 应为 `normal`
- 普通模型对比 Run 的 `parent_run_id` 应为空
- 普通模型对比 Prompt 不应强制要求模型输出参考来源
- 回答数应等于问题数乘以模型数
- 指标至少包含品牌提及率、推荐率、首推率、前三率、域名引用率和竞品提及率
- 普通模型对比结果可作为后续复测的基线 Run

---

## Scenario: 基于普通模型对比 Run 发起来源采集

假如用户已经完成一次普通模型对比 Run
当用户在该 Run 的结果页点击“采集引用来源”
那么系统应基于该普通 Run 创建一个来源采集 Run
并且系统应复用普通 Run 的品牌、域名、模拟问题、模型和竞品
并且系统只改变 Prompt 问法，要求模型输出参考来源

验收标准：
- 请求入口建议为 `POST /model-visibility/runs/{run_id}/source-probe`
- 来源采集 Run 的 `run_type` 应为 `source_probe`
- 来源采集 Run 的 `parent_run_id` 应等于原普通模型对比 Run 的 id
- 来源采集 Run 的 `source_probe_enabled` 应为 true
- 来源采集 Run 默认复用原 Run 的 `project_name`
- 来源采集 Run 默认复用原 Run 的 `domain`
- 来源采集 Run 默认复用原 Run 的 `questions`
- 来源采集 Run 默认复用原 Run 的 `providers`
- 来源采集 Run 默认复用原 Run 的 `competitors`
- 用户不需要重新填写品牌、域名、问题和模型

---

## Scenario: 来源采集只能绑定普通模型对比 Run

假如用户选择的 Run 不是普通模型对比 Run
当用户发起来源采集
那么系统应拒绝创建来源采集 Run
并提示用户需要选择普通模型对比结果作为基线

验收标准：
- 如果 `run_type = source_probe`，不允许再次基于它创建来源采集
- 如果普通 Run 不存在，应返回 404
- 如果普通 Run 不属于当前租户，应返回 404 或无权限错误
- 如果普通 Run 没有问题或模型，应返回可理解的错误提示
- 系统不应创建没有 `parent_run_id` 的来源采集 Run

---

## Scenario: 来源采集 Prompt 保留原问题并追加来源要求

假如系统正在执行来源采集 Run
当系统组装模型 Prompt
那么系统应保留原普通模型对比 Run 的每一个模拟问题
并且系统应追加“参考来源”输出要求

验收标准：
- Prompt 应包含原始用户问题
- Prompt 应包含品牌/项目名称
- Prompt 应包含官网域名
- Prompt 应要求自然回答，不要为了测试刻意堆关键词
- Prompt 应要求回答末尾增加“参考来源”部分
- Prompt 应要求尽量列出公开网页 URL、官网域名、媒体名称或文章标题
- 如果没有明确来源，模型应输出“参考来源：未找到明确公开来源”

---

## Scenario: 来源采集结果绑定回原模型对比 Run

假如来源采集 Run 已执行完成
当系统保存来源采集结果
那么系统应保存模型回答、来源抽取结果和来源文章画像
并且系统应保留它与原普通模型对比 Run 的父子关系

验收标准：
- 来源采集 Run 应保存为一条独立 `model_visibility_runs` 记录
- 来源采集回答应保存到 `model_visibility_results`
- 抽取到的来源应保存到 `ai_answer_sources`
- URL 来源应进入来源文章抓取和画像流程
- 来源采集 Run 可通过 `parent_run_id` 回查原普通 Run
- 原普通模型对比 Run 的指标和回答不应被覆盖

---

## Scenario: AI 引用偏好页面默认按模型对比 Run 展示

假如用户从模型对比结果页点击“查看引用偏好”
当系统跳转到 AI 引用偏好页面
那么页面应携带原普通模型对比 Run 的 id
并且页面应默认展示该 Run 对应的来源采集结果

验收标准：
- 跳转 URL 建议为 `/visibility-monitoring/source-preferences?parent_run_id={run_id}`
- 页面主筛选应优先展示“模型对比任务”
- 当 `parent_run_id` 存在时，统计口径应限定为该普通 Run 关联的来源采集 Run
- 页面应展示普通模型对比基础指标
- 页面应展示来源采集增强指标
- 如果该普通 Run 还没有来源采集结果，应展示“采集引用来源”按钮

---

## Scenario: 引用偏好查询支持 parent_run_id

假如系统已存在普通模型对比 Run 和对应来源采集 Run
当用户请求引用偏好接口并传入 `parent_run_id`
那么系统应只统计该普通 Run 关联的来源采集数据

验收标准：
- `GET /visibility/source-preferences?parent_run_id={run_id}` 应可用
- 查询应按当前用户租户权限过滤
- 查询应只包含 `run_type = source_probe` 且 `parent_run_id = {run_id}` 的数据
- 结果应包含来源总数、显式来源回答数、无显式来源占比、已校验来源数和已画像文章数
- 结果应包含 Top 来源域名、来源类型分布、来源校验状态分布、文章类型分布和信任锚点命中率
- 如果没有对应来源采集 Run，应返回空数据结构而不是报错

---

## Scenario: 模型对比结果页展示来源增强入口

假如用户正在查看某次普通模型对比结果
当页面渲染完成
那么页面应展示“采集引用来源”和“查看引用偏好”两个操作入口

验收标准：
- “采集引用来源”只在普通模型对比 Run 上展示
- 如果已经存在关联来源采集 Run，按钮文案可变为“重新采集引用来源”或“查看采集结果”
- 点击“采集引用来源”应调用 `POST /model-visibility/runs/{run_id}/source-probe`
- 点击“查看引用偏好”应跳转到带 `parent_run_id` 的引用偏好页面
- 来源采集执行中应有 loading 状态
- 来源采集失败应展示明确错误原因

---

## Scenario: AI 引用偏好页面不再重复创建模型对比上下文

当用户打开 AI 引用偏好页面
那么页面应把“模型对比任务”作为主筛选
并且来源采集应默认基于已选模型对比任务发起
而不是要求用户重新填写品牌、域名、问题和模型

验收标准：
- 页面主筛选应包含模型对比任务选择器
- 品牌、域名、问题和模型筛选应作为高级筛选或历史聚合筛选
- 从模型对比结果页跳转进入时，应自动选中对应模型对比任务
- 页面内点击“采集引用来源”时，应复用选中模型对比任务
- 页面应避免让用户误以为来源采集是另一套模型对比

---

## Scenario: 基于引用偏好生成优化文章

假如某个普通模型对比 Run 已完成来源采集
当用户在 AI 引用偏好页面点击“生成优化文章”
那么系统应把该普通 Run 的来源偏好画像带入文章生成
并且系统应记录文章生成任务关联的基线模型对比 Run 和来源采集 Run

验收标准：
- 文章生成请求应包含 `use_source_preference = true`
- 文章生成请求应包含 `source_preference_profile`
- 偏好画像应来自当前 `parent_run_id` 对应的来源采集结果
- 文章生成任务应能记录或回溯 `before_run_id`
- 文章生成任务应能记录或回溯 `source_probe_run_id`
- 生成文章不得复制来源文章原文
- 生成文章不得编造客户、案例、奖项、数据和资质
- 生成结果应输出信任锚点自检结果

---

## Scenario: 发布后复测使用普通模型对比口径

假如用户已经基于引用偏好生成并发布文章
当用户创建复测任务
那么系统应使用原普通模型对比 Run 的问题和模型进行复测
并且复测结果应生成新的普通模型对比 Run
而不是来源采集 Run

验收标准：
- 复测的 `before_run_id` 应指向原普通模型对比 Run
- 复测的 `after_run_id` 应指向发布后的普通模型对比 Run
- 复测不应使用来源采集 Prompt
- 复测应对比品牌提及率、推荐率、首推率、前三率、域名引用率和竞品提及率
- 复测报告应展示来源偏好发现、生成文章策略、发布后指标变化和可能归因
- 如果新发布文章被模型提及，应展示引用问题、模型、引用片段和 URL

---

## Scenario: 多次来源采集的处理

假如同一个普通模型对比 Run 已经存在来源采集 Run
当用户再次点击“采集引用来源”
那么系统应允许重新采集
并且系统应保留历史来源采集 Run
并且页面应默认使用最新一次成功的来源采集 Run

验收标准：
- 多个来源采集 Run 可以拥有同一个 `parent_run_id`
- 页面应能展示最新来源采集 Run 的结果
- 页面应能切换查看历史来源采集 Run
- 重新采集不应删除历史回答和来源
- 失败的来源采集 Run 不应覆盖最新成功结果

---

## Scenario: 数据权限和敏感信息保护

当用户查看、创建、重新采集或导出模型对比来源增强结果
那么系统应严格按租户权限过滤数据
并且不应暴露其他客户的品牌、域名、Prompt、模型回答、来源和文章画像

验收标准：
- 普通模型对比 Run 查询必须按 tenant_id 过滤
- 来源采集 Run 查询必须按 tenant_id 过滤
- `parent_run_id` 查询必须验证原 Run 属于当前租户
- 导出数据应脱敏敏感字段
- 错误日志不应输出密钥、Cookie、私有 URL 或客户敏感数据

---

## Scenario: 质量门禁

当研发完成模型对比驱动的来源增强闭环
那么系统应具备后端、前端和回归验证
并且普通模型对比的原有能力不应回归

验收标准：
- 后端测试覆盖普通 Run 创建
- 后端测试覆盖基于普通 Run 创建来源采集 Run
- 后端测试覆盖禁止基于来源采集 Run 再次创建来源采集
- 后端测试覆盖 `parent_run_id` 来源偏好查询
- 后端测试覆盖多次来源采集默认取最新成功结果
- 前端类型检查通过
- 前端 lint 通过
- 前端构建通过
- 普通模型对比 Prompt 不应被来源采集 Prompt 替换
